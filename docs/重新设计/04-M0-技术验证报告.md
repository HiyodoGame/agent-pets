## 1. 结论摘要

| 验证项 | 结论 | 等级 |
|---|---|---|
| Codex app-server 托管 | stdio JSON-RPC 可启动、建线程、发任务、收事件、中断 | 绿 |
| Codex 决策请求 | 二进制确认 requestApproval 系列方法，运行期未触发（缺登录） | 黄 |
| Claude 后台会话 | 非 TTY 下 agents --json 可用；--bg 受 workspace trust 与登录限制 | 黄 |
| Kimi 流式输出 | stream-json 可输出；重定向 HOME 可绕过沙箱存储限制，登录缺失 | 黄 |
| Kimi ACP 控制通道 | 二进制确认 session/request_permission、session/update | 黄 |

| 统一决策模型 | 方案已定，四家映射待真实登录环境确认 | 黄 |

总体判断：Codex 的 app-server 协议本身可用，但本机需要网络代理，暂不作为 M1 首切片。M1 改用 Claude Code（-p stream-json + --resume），其余按能力位与降级推进。

## 3. Codex（已验证）

### 3.1 启动

~~~powershell
$env:CODEX_HOME = '<writable-dir>'
codex app-server --listen stdio://
~~~

- stdin/stdout 走 JSON-RPC 行协议，不需要 TTY。
- 先发 initialize（带 clientInfo），再发 initialized 通知。
- 响应含 userAgent、codexHome、platformFamily、platformOs。
- codexHome 必须可写，否则初始化 sqlite 状态失败。产品里应使用用户默认 CODEX_HOME 以复用登录，只在测试时隔离。

### 3.2 关键方法（客户端到服务端）

一次未知方法请求会返回完整枚举，已确认：

- 线程：thread/start、thread/resume、thread/fork、thread/list、thread/read、thread/archive、thread/delete、thread/name/set、thread/unsubscribe
- 轮次：turn/start、turn/steer、turn/interrupt、turn/settings/update
- 队列：thread/queue/add、list、update、delete、reorder、start
- 历史：thread/turns/list、thread/timeline/list、thread/items/list（返回 not supported yet）、thread/inject_items
- 运行：thread/shellCommand、command/exec、process/spawn、process/writeStdin、process/kill、process/resizePty
- 配置与账户：config/read、config/value/write、config/batchWrite、model/list、account/read、getAuthStatus、account/login/start
- 其他：skills/list、hooks/list、mcpServer/*、fs/readFile、fs/writeFile、fs/watch、review/start

### 3.3 线程与轮次生命周期（实测）

~~~text
initialize
  -> thread/start {} => result.thread { id, cwd, model, status, path }
  -> 通知 thread/started
  -> turn/start { threadId, input:[{type:"text",text:"..."}] }
       => result.turn { id, status:"inProgress" }
  -> 通知 thread/status/changed { status:{type:"active"} }
  -> 通知 turn/started
  -> 通知 item/started / item/*/outputDelta / item/completed
  -> 通知 turn/completed { status:"completed" | "interrupted", durationMs }
  -> 通知 thread/status/changed { status:{type:"idle"} }
~~~

- thread/start 参数可以为空；默认 cwd 是启动进程目录，model 默认 gpt-6-astra。
- thread 对象带 rollout 文件路径（sessions/...jsonl），可作原始日志留档。
- turn/interrupt 需要 threadId + turnId，返回 {}；实测能把 inProgress 轮次变为 interrupted。

### 3.4 工具执行事件（实测 thread/shellCommand）

发送 thread/shellCommand {threadId, command:"echo petdeck-probe"} 后收到：

- item/started：type=commandExecution，含 command（完整 powershell 命令行）、cwd、source=userShell、status=inProgress、commandActions、aggregatedOutput=null、exitCode=null
- item/commandExecution/outputDelta：delta 分别为 "petdeck-probe" 和 "\r\n"
- item/completed：status=completed、aggregatedOutput="petdeck-probe\r\n"、exitCode=0、durationMs=799
- turn/completed：status=completed、durationMs=1003

结论：实时输出用 outputDelta 增量拼接；完成后 item/completed 的 aggregatedOutput、exitCode、durationMs 可直接用于任务结果与验收。

### 3.5 决策请求（二进制确认，运行期未触发）

codex.exe 字符串确认存在以下服务端到客户端请求：

- item/commandExecution/requestApproval
- item/fileChange/requestApproval
- item/permissions/requestApproval
- execCommandApproval（旧）
- applyPatchApproval（旧）
- requestUserInput
- mcpServer/elicitation/request
- item/tool/call

另有 serverRequest/resolved 通知。适配器应把带 id 的服务端请求统一映射为决策事件，保留请求 id，按对应结构回复。

未验证：真实模型触发命令或改文件时，请求参数字段与允许/拒绝的响应结构；需登录环境跑一次带工具调用的任务。

### 3.6 已知限制

- 未登录时 turn/start 能返回 inProgress，但不会产生模型输出事件。
- thread/read、thread/turns/list 在 rollout 为空时返回内部错误；应在 turn 完成后再读。
- thread/items/list 未实现。
- thread/queue/add 需要 clientUserMessageId；turn/interrupt 需要 turnId；turn/steer 参数结构未确认（实测发请求后无响应，可能缺字段）。

## 4. Claude Code（部分验证）

版本 2.1.312。

可用部分：

- claude agents --json 在非 TTY 下可用，返回 []；这是后台会话的机器可读入口。
- --bg/--background 启动后台会话；配套 claude attach、logs、stop、rm。
- --bg 不能与 -p/--print 同用，提示为：--bg and --print conflict，prompt 应作为位置参数。

阻塞点：

- claude --bg 在未信任目录直接拒绝：Workspace not trusted. Run claude in <dir> once and accept the trust prompt, then retry.
- 把 CLAUDE_CONFIG_DIR 指到临时目录并构造 .claude.json（hasTrustDialogAccepted=true）仍被拒绝，说明信任记录不只看该文件或结构不对。产品里应复用用户已信任的项目目录，或首次使用时引导用户点一次信任。
- 沙箱禁写用户目录，无法在保留登录态的前提下完成真实后台会话。

决策通道（待确认）：二进制中存在 can_use_tool、control_request、remote_permission_request、remote_permission_respond、permission_prompt。推测流式 JSON 以 control_request + can_use_tool 请求授权，需真实登录后抓一次工具调用确认。

## 5. Kimi Code（部分验证）

版本 2.3.0。

可用部分：

- 一次性任务：kimi -p '<task>' --output-format stream-json。
- 会话：-S/--session、-c/--continue、session/export/fork/doctor/vis/app。
- ACP：kimi acp 提供 stdio ACP server；二进制确认客户端方法包含 session/request_permission、session/update、fs/read_text_file、fs/write_text_file、terminal/create 等。

实测：

- 默认 HOME：先输出 {"role":"meta","type":"system.version","version":"2.3.0"}，随后 error: failed to run prompt: storage write failed: permission denied。
- 重定向 USERPROFILE/HOME 后：meta 正常，随后 error: failed to run prompt: No model configured. Run kimi and use /login to sign in, then retry; or set default_model in config.toml.

结论：stream-json 首条是 meta 事件；存储路径可通过 HOME 重定向解决；登录态缺失是唯一阻塞。产品里应使用用户默认 HOME。

决策通道：ACP 标准方法 session/request_permission 已确认存在，适合决策与暂停；但需实现 ACP 客户端握手与 session 生命周期，工作量高于 stream-json，M2 再评估。

## 7. Windows 进程挂起

用 PowerShell Add-Type 调 ntdll 的 NtSuspendProcess 与 NtResumeProcess，对 Start-Sleep 子进程实测，两个调用均返回 NTSTATUS 0。

结论：挂起/恢复 API 在本机可用，M1 用 koffi 在 Node 里调用同一组 API 的路线成立；koffi 打包体积与签名问题留到 M1 首个 spike。

## 8. 对 M1 的直接结论

1. 首切片改用 Claude Code：用 -p --verbose --output-format stream-json 做第一个适配器，覆盖启动、实时事件、停止、--resume 续接。Codex 的 app-server 结论保留，待代理可用后再接。
2. thread/start 传 cwd 指向任务 worktree，不复制仓库。
3. 事件映射：turn/started、item/started、item/*/outputDelta、item/completed、turn/completed、thread/status/changed 足够驱动任务详情页与桌宠状态。
4. 停止用 turn/interrupt；暂停用进程挂起（NtSuspendProcess），恢复用 NtResumeProcess，两者在产品里分开命名。
5. 追加消息优先 turn/steer（需补参数），失败则用 thread/queue/add（需 clientUserMessageId）；M1 用真实登录各测一次。
6. 决策：适配器统一发 decision 事件；Codex 先接 item/commandExecution/requestApproval 与 item/fileChange/requestApproval，参数结构在真实工具调用时补齐。
7. 不要隔离 CODEX_HOME / HOME，否则丢登录；产品使用用户默认配置目录，只把 cwd 指到 worktree。
8. Kimi、opencode 与 Codex 在 M2 逐个接；先做能力位为黄的降级路径（只读日志/只汇报），不阻塞 M1。
