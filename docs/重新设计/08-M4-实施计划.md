> 状态：已实施并完成真实环境验收（2026-11-21）。经理对话、任务拆解提案、确认派发、日报与经理模型设置均已落地；已在 Tauri 窗口内用真实 OpenAI 兼容端点（智谱 glm-4-flash）跑通「一句话 → 提案 → 确认派发 → 日报」，Mock 端点回归仍保留。2026-11-21 补充验收覆盖深色外观、8 分钟真实长任务、Ollama 端点与四项缺陷修复，详见 §9.6。
> 上游：《产品定义 v0》《交互与信息架构 v1》《架构与技术选型 v2》《M1 实施计划》《M2 实施计划》《M3 实施计划》
> 范围：经理只负责拆解、解释、汇总；没有派发、合并、停止工具。所有派发都必须由用户在界面确认。

## 1. 目标与出口

M4 把控制台从「用户自己拆任务、手动派发」推进到「用户说一句话，经理给出可编辑的任务提案，用户确认后由运行时派发」。

出口（可验收）：

1. 设置页可以配置经理模型：OpenAI 兼容 / Ollama / LM Studio / 自定义端点，填写服务地址、模型名、温度、超时与密钥；可一键测试连通。
2. 今日页左侧有经理对话；用户用自然语言描述目标，经理返回拆解提案。
3. 提案以任务卡展示：标题、项目、每个任务的标题 / 提示词 / 验收标准 / 建议 Agent / 依赖，可调整后保存，也可放弃。
4. 确认之前不创建任何任务；只有点击「确认派发」才创建任务并触发派发。
5. 确认派发后：独立任务立即启动，有依赖的任务保持待开始，等前置任务完成后进入调度。
6. 汇报页展示按天日报：涉及任务、完成、待验收、待合并、需处理、待决策与正文；经理不可用时用本地汇总兜底。
7. 经理 API 密钥不回传前端；经理工具集只有 propose_tasks，没有派发、合并、停止能力。
8. typecheck、单测、桥接测试、lint、production build 通过。

## 2. 范围

### 做

- SQLite v4：manager_messages、proposals、reports 三张表与迁移。

- 经理工具：propose_tasks（1–8 个任务，含依赖与优先级）。
- 运行时：经理设置、测试连通、对话、提案更新/确认/放弃、日报生成与读取。
- 桥接：manager / proposals / reports 路由。
- 控制台：今日页经理面板与提案卡、汇报页、设置页经理模型区。
- 真实 UI 走查：本地 Mock OpenAI 端点 + 真实 bridge + Playwright。

### 不做（留给 M5 或后续）

- 订阅账号（Claude/Codex CLI）作为经理后端；当前只做 OpenAI 兼容接口。

## 3. 数据模型（SQLite v4）

SCHEMA_VERSION = 4，仍用 PRAGMA user_version 迁移，v3 库自动建表，不重建。

### 3.1 manager_messages

| 列 | 说明 |
| --- | --- |
| id | 消息 id |
| role | user / assistant / system |
| content | 正文 |
| proposal_id | 关联提案（assistant 消息） |
| meta_json | 模型、usage 等 |
| created_at | 毫秒时间戳 |

索引：created_at。读取时按时间正序返回，默认最近 100 条。

### 3.2 proposals

| 列 | 说明 |
| --- | --- |
| id | 提案 id |
| project_id | 目标项目；确认派发时必填 |
| title / summary | 提案标题与摘要 |
| status | pending / confirmed / rejected |
| items_json | 任务项数组 |
| task_ids_json | 确认后真实任务 id |
| created_at / updated_at / confirmed_at | 时间 |

索引：(status, created_at)。提案不超时；只能由用户确认或放弃。

### 3.3 reports

| 列 | 说明 |
| --- | --- |
| id | 日报 id |
| report_date | 本地日期 YYYY-MM-DD |
| project_id | 空字符串表示全部项目 |
| title / body | 标题与 Markdown 正文 |
| stats_json | 统计与来源信息 |
| source | manager / local |
| created_at / updated_at | 时间 |

唯一约束：(report_date, project_id)。同一天同一范围重新生成会覆盖，不堆重复日报。

### 3.4 settings

经理配置存在既有 settings 表的 manager 键：provider、baseUrl、model、temperature、timeoutMs、apiKey。读取时与 MANAGER_DEFAULTS 合并。

## 4. 经理客户端

实现：petdeck/server/runtime/manager.mjs。

### 4.1 Provider preset

| provider | 默认 baseUrl | 需要密钥 |
| --- | --- | --- |
| openai | https://api.openai.com/v1 | 是 |
| ollama | http://127.0.0.1:11434/v1 | 否 |
| lmstudio | http://127.0.0.1:1234/v1 | 否 |
| custom | 空，由用户填写 | 否 |

- 请求地址：baseUrl 尾部没有 /chat/completions 时自动追加。
- 认证：有 apiKey 时发 Authorization: Bearer。
- 密钥优先级：设置里保存的 key → PETDECK_MANAGER_API_KEY → OPENAI_API_KEY（后两者只对 openai/custom 生效）。
- ready 的判断：有 baseUrl、有 model，且（有 key 或 provider 不需要 key）。OpenAI 无 key 时不算就绪，避免点到才报错。

### 4.2 错误码

MANAGER_NOT_CONFIGURED、MANAGER_KEY_MISSING、MANAGER_TIMEOUT、MANAGER_UNREACHABLE、MANAGER_HTTP_ERROR、MANAGER_BAD_RESPONSE。桥接把它们转成 409/502 与可读 message，不把上游响应体里的密钥回传。

### 4.3 工具与系统提示

- 唯一工具：propose_tasks。
- 参数：summary + tasks[1..8]，每项含 ref、title、prompt、acceptance、agent（claude-code / kimi-code / opencode）、depends_on、priority（0–100）；可选 project_id。
- 系统提示明确：经理只拆解、解释、总结；没有派发、合并、停止权限；必须等用户确认；任务提示词要能独立执行，并写清验收标准；不编造事实。
- 用户消息若模型没有调用工具，会尝试从回复里的 JSON 代码块兜底解析；再失败就只返回对话，不造提案。

### 4.4 上下文

buildManagerContext 只喂结构化摘要，不喂全量事件流：

- 项目元数据（名称、路径、是否 git）。
- 最近 50 个任务（标题、状态、Agent、摘要）。
- 待确认提案。
- 待决策。
- 最近 3 份日报。

历史对话只带最近 20 条，避免上下文无限增长。

## 5. 提案与派发

### 5.1 生成

POST /api/runtime/manager/messages { content, projectId }：

1. 校验文本 ≤ 8000 字符、项目存在、经理已就绪。
2. 先保存 user 消息。
3. 调经理，拿到文本与 propose_tasks。
4. 归一化任务项：1–8 个，标题 ≤ 200，提示词 ≤ 20000，验收标准 ≤ 2000；ref 去重；依赖只能引用本次提案里的 ref，做 DFS 环检测；未知 Agent 回退默认 Agent。
5. 有提案则写 proposals（pending），assistant 消息带 proposal_id；文本为空时用「我拆成了 N 个任务，确认后才会派发。」
6. 返回 { message, proposal }；此时 tasks 表仍为空。

### 5.2 调整与放弃

- POST /proposals/:id/update：仅 pending；可改标题、摘要与任务项，重新跑同一套归一化与依赖校验。
- POST /proposals/:id/reject：仅 pending，状态改 rejected，写一条 system 消息；不创建任务。

### 5.3 确认派发

POST /proposals/:id/confirm { start }：

1. 仅 pending；没有 project_id 返回 PROPOSAL_PROJECT_REQUIRED。
2. 逐个创建任务：prompt 末尾追加「验收标准」；permissionMode 默认 acceptEdits；写入 priority。
3. 建立 ref → 真实 task id 的映射，再回写 depends_on。
4. 提案改 confirmed，记录 task_ids 与 confirmed_at，写 system 消息。
5. start=true 时逐个派发：先重新读取任务再判断依赖，依赖未满足的返回 { deferred: true }，不误启动；独立任务正常启动，容量不足则排队。
6. 返回 { proposal, tasks, started }；单个任务启动失败只记在该项的 error，不整体回滚已创建任务。

## 6. 日报

POST /api/runtime/reports/generate { date, projectId }：

1. 取本地日界内 updated_at 的任务，附项目名、最多 6 个产物、待决策与待确认提案。
2. 统计：涉及任务、完成（completed+merged）、待验收、待合并、运行、排队、暂停、待决策、失败、停止、待决策数、待提案数。
3. 先用确定性本地汇总生成 Markdown（今日产出 / 进行中 / 遇到的问题 / 等你处理 / 明天建议），保证经理不可用也有内容。
4. 经理 ready 时再调用模型，要求同样五个二级标题、≤700 字；返回内容 >30 字才采用，并标 source=manager。
5. 经理失败不阻塞日报，stats.manager_error 记录原因，正文保留本地汇总。
6. 同一天同一项目 upsert，不重复堆叠。

前端 ReportsView 只渲染 Markdown 子集（## / ###、- 列表、空行分段），全部用 React 节点，绝不 innerHTML。

## 7. API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/PUT | /api/runtime/manager/settings | 读取 / 更新经理模型；PUT 不返回密钥 |
| POST | /api/runtime/manager/test | 发「只回复 OK」测试连通 |
| GET/POST | /api/runtime/manager/messages | 历史消息 / 发送一句话 |
| GET | /api/runtime/proposals?status= | 提案列表，默认 pending |
| POST | /api/runtime/proposals/:id/confirm | body { start } |
| POST | /api/runtime/proposals/:id/reject | body { reason } |
| POST | /api/runtime/proposals/:id/update | body { title, summary, items } |
| POST | /api/runtime/reports/generate | body { date, projectId } |
| GET | /api/runtime/reports?projectId=&limit= | 日报列表 |
| GET | /api/runtime/reports/:id | 日报详情 |

所有写请求继续走 readJsonWrite：Origin 白名单、token、JSON 类型、体积上限。读请求走 readGuard。

### 7.1 CORS 修复

走查发现浏览器保存经理设置时报 Failed to fetch，上游是 preflight 被拒：

    Method PUT is not allowed by Access-Control-Allow-Methods in preflight response.

桥接原先只声明 GET,POST,OPTIONS，但 M2 的设置保存用 PUT、M3 的产物删除用 DELETE。已改为：

    Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS

并新增桥接测试断言 preflight 必须包含这五个方法。该修复同时解除了调度设置保存与产物删除在浏览器里的隐藏故障。

#### 补充验收中修复的四个缺陷

1. **经理回复被 tool-call 流污染**：智谱 glm-4-flash 把 `{"index":0,"finish_reason":"tool_calls",...}` 拼进 `message.content`，原实现直接保存。`manager.mjs` 新增 `stripToolCallEcho(content, toolCalls)`，仅在确有 toolCalls 且 content 出现 tool-call 流片段时截断；`chat()` 统一清洗。manager.test 覆盖三种输入，真实 HTTP E2E 的 assistant 正文为「我拆成了两个任务，确认后才会派发。」，无污染片段。
