# 自动更新与签名

PetDeck 使用 Tauri 2 updater：桌面版从 GitHub Releases 的 `latest.json` 检查新版本，下载经过 Minisign 签名校验的 NSIS 更新包，用户确认后安装并重启。

## 端点与产物

- 更新端点：`https://github.com/HiyodoGame/agent-pets/releases/latest/download/latest.json`
- **仓库必须为 public**（或更新端点匿名可读）。私有仓库的 release 资源需要鉴权，桌面端更新器无法匿名读取。
- 公钥：写在 `petdeck/src-tauri/tauri.conf.json` 的 `plugins.updater.pubkey`
- 发布产物（由 `.github/workflows/release.yml` 调用 lockfile 固定的本地 Tauri CLI 构建与签名）：
  - `PetDeck_<version>_x64-setup.exe`（NSIS 安装包）
  - 更新包与 `.sig` 签名
  - `latest.json`（版本、GitHub Release 直接下载地址、签名；发布前由工作流在本地生成并用 `release:check --file` 校验）

## 签名密钥

本机生成的密钥（**不入库**）：

- 私钥：`C:\Users\Con_WKK\.tauri\petdeck-updater.key`
- 公钥：`C:\Users\Con_WKK\.tauri\petdeck-updater.key.pub`（内容已写入 `tauri.conf.json`）
- 密码：`C:\Users\Con_WKK\.tauri\petdeck-updater.password`

需要在 GitHub 仓库 Settings → Secrets and variables → Actions 中添加：

| Secret | 值 |
| --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | 私钥文件的完整内容 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 上面 `.password` 文件的内容 |

**务必备份私钥与密码。** 丢失后，已安装的客户端将无法验证新版本签名；只能更换密钥并让用户手动重装一次。

> 私钥和密码不得提交到仓库、不得贴进 issue / 日志 / CI 输出。

## 发布流程

### tag 前（本地 + CI）

1. 版本号四处一致：
   - `petdeck/package.json`
   - `petdeck/src-tauri/Cargo.toml`
   - `petdeck/src-tauri/Cargo.lock`（`petdeck` 包块）
   - `petdeck/src-tauri/tauri.conf.json`
   （`npm run docs:check` 会校验前三处与文档版本是否一致。）
2. `CHANGELOG.md` 的 `## [Unreleased]` 收口为 `## [x.y.z] — YYYY-MM-DD`，并保留一个空的 `Unreleased`。
3. 质量门全绿：

   ```bash
   npm test
   npm run typecheck
   npm run lint
   npm run build
   npm run docs:check
   cargo test --manifest-path src-tauri/Cargo.toml
   ```

4. 提交并推送 `master`，确认 `CI` 与 `Desktop CI` 全绿（tag 会绕过分支保护，红着打 tag 等于把问题发给用户）。
5. 打 tag 并推送：

   ```bash
   git tag -a v0.2.1 -m "PetDeck v0.2.1"
   git push origin v0.2.1
   ```

### tag 后（发布核对）

0. 想在不打 tag 的前提下验证整条链路，用 `Release` 工作流的 **`workflow_dispatch` 干跑**（Actions 页 Run workflow，或 `gh workflow run release.yml --ref master`）：跑完版本一致性、构建签名、验签、静默安装与 manifest 校验，**跳过 tag 比对与草稿上传**，不创建也不改动任何 Release。2026-11-24 已实跑通过（run 45319419568，安装包 29.7 MB）。
1. `Release` 工作流先核对 tag 与 package/Cargo/Cargo.lock/Tauri 版本，再构建、签名、检查安装包内容、用 updater 公钥做密码学验签，并在本地生成和校验 `latest.json`。**这些步骤全部通过前不会创建或公开 Release。**
2. 验证通过后，工作流只创建/更新 **draft Release**，上传 NSIS 安装包、`.sig` 与 `latest.json`。若同 tag 已是公开 Release，工作流会拒绝覆盖其资产。
3. 维护者在 GitHub 草稿页核对版本、说明和 assets 三件套，必要时下载草稿安装包做最终烟测，然后人工发布。工作流失败时只需修复后重跑同 tag 的草稿流程，不需要撤回一个已经公开的坏包。
4. 人工发布后，等 GitHub `releases/latest` 指向新版本，再跑真实清单自检：

   ```bash
   npm run release:check                 # 拉取真实 latest.json，校验结构、签名长度、版本号
   npm run release:check -- --expect 0.2.1
   ```

   失败时脚本以退出码 1 结束并逐条列出问题（结构缺失、签名过短、版本不匹配、平台条目缺失）。
5. 用上一版安装包实测一次：发现 → 下载（进度条）→ 验签 → 安装 → 重启 → 版本正确。

### 回滚

- 不要把同一个版本号重发一次（SemVer 与客户端缓存都会错乱）；紧急修复发补丁版本 `x.y.z+1`。
- 需要立刻止损时，在 GitHub 上把问题 Release 改为 **pre-release** 或删除：`releases/latest/download/latest.json` 会回落到上一个正式 Release，已装新版客户端不会再被推广到坏版本。
- 若只是想撤回某条更新说明，改 Release 描述即可；`latest.json` 的 `notes` 下次发版自然覆盖。

### 更新失败的用户可见分类

设置页「关于与更新」按下表给出可读文案与重试入口（原始错误同时写入 `sidecar-*.log` 的 `update.*` 行）：

| 分类 | 触发条件（示例） | 文案要点 |
| --- | --- | --- |
| 网络不可达 | 连接超时、DNS、TLS、502/503/504、代理拦截 | 检查网络或代理后重试 |
| 签名校验失败 | `signature verification failed`、Minisign 公钥不匹配 | 安装包可能损坏或被篡改，已中止安装 |
| 磁盘写入失败 | `os error 28/112`、`Access is denied` | 检查磁盘空间与权限后重试 |
| 其他 | 以上都不匹配 | 稍后重试或从 Releases 手动下载 |

`v0.1.0` 没有内置 updater，无法自动升级到 `v0.1.1`。用户需要手动下载并安装一次 [v0.1.1](https://github.com/HiyodoGame/agent-pets/releases/tag/v0.1.1)；从 `v0.1.1` 起，后续版本可在应用内更新。

## 本地验证

- 打包含签名更新产物：
  ```bash
  TAURI_SIGNING_PRIVATE_KEY="$(cat <私钥路径>)" \
  TAURI_SIGNING_PRIVATE_KEY_PASSWORD=<密码> \
  npm run tauri:build
  ```
  > Tauri CLI 2.12.4 读取 `TAURI_SIGNING_PRIVATE_KEY` 的内容；`TAURI_SIGNING_PRIVATE_KEY_PATH` 在当前版本未生效。
- 仅验证编译（不打包、不签名）：
  ```bash
  npm run tauri:build -- --no-bundle
  ```
- 真正的端到端升级验证：安装一个较旧的已签名版本 → 发布一个更高版本 → 打开「宠物设置 → 自动更新」确认能发现新版本、安装并重启。该链路依赖已发布的 Release，发布前不能仅靠单测证明。
